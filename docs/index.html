Overview

Dyvine wraps the third-party f2 Douyin SDK as a hermes plugin. There is no HTTP surface: plugin.yaml plus register(ctx) is the only interface, distributed both as a directory plugin (Git URL) and as a pip package (hermes_agent.plugins entry point).

  • 35 idempotent, single-shot tools take a JSON object and return a JSON string.
  • Async, fire-and-forget downloads return an operation_id immediately and continue on tracked background tasks; poll with the matching status tool.
  • Persistent state lives in a shared Postgres database (schema versioned by Alembic): operations, download queue, seeds, send status, profiles, rounds, and watch subscriptions.
  • Idle-quiet by design: importing the plugin performs zero network I/O and opens zero connections; the engine boots on the first tool call.
  • User-supplied output paths are resolved inside DOUYIN_DOWNLOAD_ROOT and rejected when they escape the configured root.
  • Dedicated thread pools isolate R2 calls and R2 metadata fan-out; database IO is natively async over asyncpg.
  • A bundled dyvine:dyvine-ops skill carries the batch-delivery SOP plus the tool manual.
DomainPurpose

PostsPer-post detail, paginated listing, comments, stats, feeds, and bulk download (post/like/collection/music/mix/collects).

Install

From the hermes catalog (once listed):

hermes plugins install dyvine

From Git:

hermes plugins install <owner>/dyvine --enable

From pip (entry-point distribution):

pip install dyvine
# then enable `dyvine` in hermes (`hermes plugins enable dyvine`)

At install hermes prompts for the required environment (requires_env):

DATABASE_URL=postgresql+asyncpg://user:password@host:5432/dyvine
DOUYIN_COOKIE=<browser session cookie>
Feishu credentials are not plugin inputs. Delivery reads the hermes defaults (FEISHU_APP_ID/FEISHU_APP_SECRET from ~/.hermes/.env) at runtime. Channels other than Feishu groups go through hermes-native messaging; dyvine.notify.send is a thin wrapper, not a channel implementation.

Apply the schema once before first use (operator-side, from a repo checkout with the same DATABASE_URL):

uv run alembic upgrade head

Hermes dependency resolution

Hermes resolves a directory plugin's pyproject.toml [project].dependencies (plugin.yaml python_dependencies only when there is no pyproject.toml) against the pins of its own environment. Dyvine's floors admit those pins (core python-dotenv==1.2.2, bedrock extra boto3==1.42.89; test-pinned), but f2 0.0.1.7 publishes == pins (httpx==0.27.2, pydantic==2.9.*, websockets<13, protobuf==5.28.3, ...), so hermes plugins enable dyvine still reports "No solution found". The lockfile lifts those pins with [tool.uv] override-dependencies, which Hermes does not read, and the plugin runs on the Hermes versions of the shared packages.

Install the locked packages that the Hermes venv lacks, without their dependencies, and leave every package Hermes already has at its version. Run the commands from a checkout at the deployed revision; HERMES_PY is the interpreter of the venv that runs hermes: 

HERMES_PY=/path/to/hermes-agent/venv/bin/python
uv export --frozen --no-dev --no-emit-project --no-hashes --no-header \
  --no-annotate -o dyvine-locked.txt
"$HERMES_PY" - dyvine-locked.txt > dyvine-missing.txt <<'EOF'
import re, sys
from importlib.metadata import PackageNotFoundError, version
for line in open(sys.argv[1]):
    req = line.strip()
    if not req or req.startswith("#"):
        continue
    try:
        version(re.split(r"[\s;=<>!~\[]", req, maxsplit=1)[0])
    except PackageNotFoundError:
        print(req)
EOF
uv pip install --no-config --python "$HERMES_PY" --no-deps -r dyvine-missing.txt

--no-config stops uv from applying the checkout's [tool.uv] override-dependencies, which would replace some locked pins with open floors. Repeat these steps after every hermes update: the update can drop the added packages and disable the plugin. Afterwards, confirm with hermes plugins list that dyvine is enabled, restart the gateway (hermes gateway restart), and make one signed read-only call such as dyvine.posts.list.

Plugin doctor and a profile call do not exercise the request signer. During the cutover both passed while the Playwright dependency pyee from uv.lock was missing, and signed post-list calls returned HTTP 403 until it was installed. Verify the matching Chromium build and read one authorized dyvine.posts.list page before enabling weekly sends.

Chromium for the webSign signer

playwright==1.62.0 expects Chromium revision 1234 (Chrome for Testing 151.0.7922.34). Install it as the user that runs the Hermes gateway, with the same PLAYWRIGHT_BROWSERS_PATH if the gateway sets one. Where the default Playwright CDN is slow, point PLAYWRIGHT_CHROMIUM_DOWNLOAD_HOST at a mirror that serves the same path layout, for example npmmirror: 

PLAYWRIGHT_CHROMIUM_DOWNLOAD_HOST=https://cdn.npmmirror.com/binaries/playwright \
  "$HERMES_PY" -m playwright install chromium

The variable covers every chromium* download and takes precedence over PLAYWRIGHT_DOWNLOAD_HOST. On linux x64 the signer's build is fetched from <host>/builds/cft/151.0.7922.34/linux64/chrome-linux64.zip, so a local HTTP server that serves the official Chrome for Testing zip under that path works too.

Quick Start

Prerequisites

  • uv or Python 3.12+
  • Git
  • Postgres 16+ (all plugin state lives in Postgres)
  • A valid Douyin session cookie
  • Optional Cloudflare R2 credentials and bucket for archival uploads

Develop

git clone https://github.com/memenow/dyvine.git
cd dyvine
uv sync --all-extras
cp .env.example .env   # set DOUYIN_COOKIE, DATABASE_URL
docker run -d --name dyvine-pg \
  -e POSTGRES_USER=dyvine -e POSTGRES_PASSWORD=dyvine \
  -e POSTGRES_DB=dyvine -p 5432:5432 postgres:16
uv run alembic upgrade head

Validate

make test       # pytest
make coverage   # pytest with the 80% gate
make lint       # ruff + mypy
make format     # black + isort
make doctor     # hermes plugins doctor --ci (needs docker)

Optional R2 archival requires R2_ACCOUNT_ID, R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY, R2_BUCKET_NAME, and R2_ENDPOINT. The storage service auto-disables when any R2 field is empty.

Set DOUYIN_RETAIN_LOCAL_DOWNLOADS=true to run in local-retention mode: each task's files are kept under DOUYIN_DOWNLOAD_ROOT/tasks/<task_id> instead of being swept after upload, and the upload step is skipped while R2 is unconfigured. Retention also applies implicitly whenever R2 is unset, so a finished download is never discarded. Bound the retained workspace with DOUYIN_RETAIN_MAX_GB (GiB; 0 disables pruning).

Douyin's web APIs additionally require a per-request Argus webSign triple (uifid/timestamp/x-secsdk-web-signature) that only the SecureSDK inside a real browser session can compute. Dyvine keeps one headless-Chromium page purely as a signing session -- all traffic and downloads stay on plain HTTP -- starting it lazily on the first signed request (DOUYIN_WEBSIGN_ENABLED, default true; page DOUYIN_WEBSIGN_PAGE_URL; budgets DOUYIN_WEBSIGN_INIT_TIMEOUT_SECONDS and DOUYIN_WEBSIGN_SIGN_TIMEOUT_SECONDS), and re-signs once with a fresh session when it observes an Argus block (DOUYIN_WEBSIGN_RETRY_ONCE), and fails fast (backing off) after repeated signer failures. The host must provide a matching Chromium build (uv run playwright install chromium from a checkout; see Chromium for the webSign signer); without it the builders return unsigned URLs exactly as before, so unaffected endpoints keep working while gated ones fail as HTTP 403. Set DOUYIN_WEBSIGN_ENABLED=false only as a kill-switch.

Persistence targets Postgres: set DATABASE_URL to a postgresql+asyncpg:// connection string and pick a pool strategy with DATABASE_POOL_CLASS: null (default) opens a fresh connection per use and holds none while idle, while queue keeps a capped pool tuned by DATABASE_POOL_SIZE, DATABASE_POOL_MAX_OVERFLOW, DATABASE_POOL_TIMEOUT, DATABASE_POOL_RECYCLE_SECONDS, and DATABASE_POOL_PRE_PING. DATABASE_OPERATION_RETENTION_DAYS bounds how long terminal operation rows are kept (0 disables purging), and DATABASE_JANITOR_INTERVAL_SECONDS (0 = disabled) controls the janitor heartbeat/sweep cadence. Apply schema changes with uv run alembic upgrade head.

Weekly Delivery & Migration

The bundled dyvine:dyvine-ops skill carries the full batch-delivery SOP. The durable rules, condensed:

  • Never send a bare text probe: the first message in a delivery group is always the author's profile link + nickname.
  • Use DYVINE_WEEKLY_GROUP_POLICY=reuse_existing in every round. A returning account is identified by stable sec_user_id and reuses one Postgres-verified historical chat and topic; only a new account gets a new group with the recipient's ou_ open ID as owner_id.
  • Process legacy backfill in verified batches of two accounts. The bounded weekly runner finishes each pair before it starts the next; do not clean local files until delivery is reconciled.
  • The durable sender records 0-byte files and files above its 29 MiB upload cap as permanent failures. It leaves local media in place for reconciliation.
  • Backfill dedupe uses file-level ledger records and confirmed historical messages, not nickname counters. A 0/0 summary is not evidence that no media was missed.
  • Run same-nickname accounts (distinct sec_user_ids) serially during backfill: legacy download directories and progress keys were nickname-based.
  • Batch URL input: regex-extract v.douyin.com links from pasted share texts and resolve each with dyvine.users.resolve.
  • Leak scan orders each account's latest operation by created_at. Concentrated mass failures usually mean an expired DOUYIN_COOKIE; scattered interrupted after a refresh means Douyin-side volume throttling — converge over multiple rounds.

Weekly runner

hermes dyvine weekly run-once advances ordered pairs of accounts back to back in seed order within a bounded runtime and file count. It waits for every download started by that invocation and saves its checkpoint to Postgres before exiting. It does not advance to the next pair until both current accounts have terminal outcomes. A new pair starts only within the first 15 minutes of an invocation, while no review state was hit, and while the pair's estimated download fits the free disk space minus max(10 GiB, 10% of the disk). The estimate is 2 GiB per full-feed account (full mode or no cutoff) and, for an incremental account, 1.5 times its days since the queue cutoff times the round's download rate: the 90th percentile of bytes per window day among its finished accounts, or 20 MiB per day until 10 of them recorded one. The first pair must fit too; a disk_budget outcome means nothing was started. A row still parked in needs_reconciliation does not hold later pairs, but it keeps blocking automatic rounds until it is reconciled. An incremental download stops at the queue cutoff: media posted at or before it is neither downloaded nor sent, so a first run without a saved anchor fetches only the round's window, not the account's whole feed. With no --round, it creates a weekly-YYYY-MM-DD round at or after Sunday 08:00 in DYVINE_WEEKLY_TIMEZONE=Asia/Shanghai. Its incremental cutoff is the Sunday 08:00 of the latest earlier automatic round that was opened; the first round uses the Sunday before the first eligible one. A week held back by an unfinished round therefore widens the next window instead of being skipped. The required DYVINE_WEEKLY_FIRST_AUTO_DATE is the first eligible Sunday (YYYY-MM-DD); earlier automatic rounds are not opened. The required DYVINE_WEEKLY_CUTOVER_ROUND names the active legacy round. It and unfinished automatic rounds dated from the first eligible Sunday onward block a new automatic round. Older frozen rounds remain available for reconciliation without blocking the schedule. --round selects an existing round without the schedule guard; --dry-run inspects the next candidate without queue or delivery writes. 

hermes dyvine weekly run-once --dry-run
hermes dyvine weekly run-once --round weekly-YYYY-MM-DD --dry-run
hermes dyvine weekly run-once --round weekly-YYYY-MM-DD

Configure DYVINE_WEEKLY_TIMEZONE=Asia/Shanghai, DYVINE_WEEKLY_FIRST_AUTO_DATE (the first intended automatic Sunday), DYVINE_WEEKLY_CUTOVER_ROUND (the active legacy round), DYVINE_WEEKLY_GROUP_POLICY=reuse_existing, and DYVINE_WEEKLY_OWNER_OPEN_ID (a recipient ou_ ID) in the Hermes runtime environment. The runner uses 2026-09-27 and a privately configured active legacy round for this cutover; these are deployment values, not project defaults. It also reads DATABASE_URL, DOUYIN_COOKIE, FEISHU_APP_ID, FEISHU_APP_SECRET, and DOUYIN_DOWNLOAD_ROOT. The plugin declares Playwright as a dependency; install its matching Chromium browser on the host. The CLI rejects an unset or unknown group policy. In the frozen cutover inventory, 1,619 of 1,631 accounts present in multiple rounds reused one chat. Returning accounts with missing or conflicting chat or topic evidence remain on hold for manual reconciliation.

Legacy disk-state migration

  1. Pause the old weekly cron and its auto-restart path at an account boundary. Record the queue, weekly progress files, local media, group IDs, and Feishu messages from the same frozen point.
  2. Keep the original download directory mounted at the same path. Apply uv run alembic upgrade head against the intended RDS database.
  3. Read the migration dry-run counts and issues before importing the frozen files. The database URL comes from DATABASE_URL, not a command argument.
  4. Stage the legacy per-file send progress and write a private reconciliation report. Review it, then import the frozen source without --dry-run. Exit code 1 means historical paths need review; exit code 2 means a source or configuration error. This importer records path evidence; it does not adopt groups.
  5. Preview legacy group adoption for the active round and review each live Feishu chat/topic result. Apply only the verified results, then audit the full chat and topic-thread history, including zero-file groups.
  6. Reconcile imported weekly entries against file-level media and Feishu message IDs. Entries found only in weekly progress files stay needs_reconciliation and cannot be claimed until verified. Preserve the legacy files and media through acceptance.

The importer inserts by natural key without replacing existing rows, so reruns can validate the same frozen source. The progress import's dry run writes a local staging database and JSONL but does not write RDS. If the frozen source includes permanent_failures.json or report_sent_index.json, add --permanent-failures PATH or --sent-index PATH to both the dry run and write run. Start a new --work-db before adding either source to a previous staging run. Unambiguous, conflict-free permanent failures enter the ledger to prevent a repeat attempt; cache-only sent-index paths remain unverified audit evidence and do not count as delivered. Only sent paths with a unique nickname-to-account mapping and no collision become legacy_confirmed_sent; failed and ambiguous paths remain audit evidence, and queue entries stay blocked. A migration report or nickname-level send counter does not prove individual delivery. New file ledger records key a media item by account, account-relative path, and content hash; it retains the upload file_key, send UUID, and Feishu message ID. A legacy send covers a re-downloaded file with the same account-relative path, or with the same post creation stamp and media slot (_video.mp4, _image_3.webp, ...) when a caption edit renamed it, so the file is not sent twice. Consecutive weekly windows overlap, so a confirmed send by this runner covers a caption-renamed re-download the same way. Upload names longer than 50 characters are shortened; post media keeps its slot suffix, so the images of one post keep distinct names in the group. The Feishu audit and the window proof still match legacy uploads by the legacy truncation (the first 40 characters of the stem plus the extension). A file reply goes into the verified topic thread. Unknown group, topic, or file-send outcomes remain on hold after their safe UUID retry windows for message-level reconciliation; do not replay solely because a summary count is missing. Confirmed historical files suppress automatic resend. Only confirmed unsent files are candidates for backfill.

Watch Mode

Watch Mode turns Dyvine from a request-driven downloader into a monitor. Each subscription targets one Douyin user and runs a long-lived asyncio loop with two independent polling cadences: a live-status check and a new-post check. When a live check finds the user streaming, it delegates to the livestream downloader (deduped by room_id). When a post check finds new content, it delegates to the incremental post downloader. Both paths create normal operation rows observable through the operation-polling tools.

Behavior and invariants

  • Each cadence uses monotonic due-times with +/−10% jitter so multiple subscriptions never hammer the upstream in lockstep.
  • With backfill_on_create=false (the default), the service snapshots the user's current first page of posts at creation time. The first post check then stops pagination at that boundary and downloads only posts published afterward.
  • New-post deduplication is membership-based using a bounded recent-aweme_id set (capped by DOUYIN_WATCH_RECENT_ID_CAP). The checkpoint is only advanced after a successful run so an interrupted cycle re-downloads at most the most-recent window, which the f2 downloader overwrites idempotently.
  • A live check delegates to the existing livestream downloader; a live-status miss or an already-in-progress recording is silently skipped.
  • Each triggered download creates a regular operation row (livestream_download or user_posts_incremental_download) pollable through the operation tools.
  • Subscriptions survive restarts: they are persisted in a dedicated watch_subscriptions Postgres table (same database as the operations table) and all enabled subscriptions are re-armed automatically on startup.
  • A crashed watcher loop restarts under exponential backoff and parks after 5 consecutive crashes; a parked subscription resumes only after delete-and-recreate.
  • Watch scheduling splits with WATCH_ENABLED: CRUD-only processes run with false (no loops run locally) while exactly one watcher process runs the loops and adopts new rows through a periodic reconcile pass.

Operations

Persistent State Store

src/dyvine/db/postgres.py persists operations, queue entries, seeds, send status, delivery ledger records, profiles, rounds, and watch subscriptions in Postgres (SQLAlchemy 2.0 async over asyncpg), connecting to DATABASE_URL. The schema is versioned by Alembic: run uv run alembic upgrade head before tools run against a new revision.

  • Every operation row carries an owner_id and a heartbeat timestamp.
  • With an explicit DATABASE_JANITOR_INTERVAL_SECONDS, the janitor heartbeats owned rows and fails rows whose owner went quiet; only genuinely orphaned rows are touched. Single processes run boot recovery plus a daily retention purge only, and never touch the database while idle.
  • Terminal rows older than DATABASE_OPERATION_RETENTION_DAYS are purged at boot and daily.
  • Read-only lookups never touch the stores; only real task execution opens database connections (pinned by tests/test_stateless_contract.py).
  • Unit tests inject in-memory fakes; the contract suite in tests/db/ runs identical assertions against both backends.

Background Task Lifecycle

Long-running downloads are scheduled through BackgroundTaskRegistry. During shutdown, tracked tasks drain before executor pools are reaped. State always lands in Postgres first, so a gateway restart loses at most in-flight progress, never records.

Idle Health

Repositories record each call's outcome in a DatabaseHealthTracker (unknown/available/unavailable plus a checked-at timestamp) observed from real calls, so idle health readers consult last-known state instead of probing. unknown counts as healthy.

Security Notes

  • Non-debug settings reject the placeholder database default.
  • Livestream URL validation only accepts douyin.com family hosts.
  • Output paths are checked before and after directory creation, including symlink segment detection.
  • Feishu credentials come from hermes defaults at runtime — never from the repo, Postgres, or logs. Never commit secrets, cookies, real user IDs, or local environment files.
  • Tool error messages stay human-readable and secret-free; the registry renders propagated errors.
