Overview

Dyvine wraps the third-party f2 Douyin SDK as a hermes plugin. There is no HTTP surface: plugin.yaml plus register(ctx) is the only interface, distributed both as a directory plugin (Git URL) and as a pip package (hermes_agent.plugins entry point).

  • 35 idempotent, single-shot tools take a JSON object and return a JSON string.
  • Async, fire-and-forget downloads return an operation_id immediately and continue on tracked background tasks; poll with the matching status tool.
  • Persistent state lives in a shared Postgres database (schema versioned by Alembic): operations, download queue, seeds, send status, profiles, rounds, and watch subscriptions.
  • Idle-quiet by design: importing the plugin performs zero network I/O and opens zero connections; the engine boots on the first tool call.
  • User-supplied output paths are resolved inside DOUYIN_DOWNLOAD_ROOT and rejected when they escape the configured root.
  • Dedicated thread pools isolate R2 calls and R2 metadata fan-out; database IO is natively async over asyncpg.
  • A bundled dyvine:dyvine-ops skill carries the batch-delivery SOP plus the tool manual.

Install

From the hermes catalog (once listed):

hermes plugins install dyvine

From Git:

hermes plugins install <owner>/dyvine --enable

From pip (entry-point distribution):

pip install dyvine
# then enable `dyvine` in hermes (`hermes plugins enable dyvine`)

At install hermes prompts for the required environment (requires_env):

DATABASE_URL=postgresql+asyncpg://user:password@host:5432/dyvine
DOUYIN_COOKIE=<browser session cookie>
Feishu credentials are not plugin inputs. Delivery reads the hermes defaults (FEISHU_APP_ID/FEISHU_APP_SECRET from ~/.hermes/.env) at runtime. Channels other than Feishu groups go through hermes-native messaging; dyvine.notify.send is a thin wrapper, not a channel implementation.

Apply the schema once before first use (operator-side, from a repo checkout with the same DATABASE_URL):

uv run alembic upgrade head

Quick Start

Prerequisites

  • uv or Python 3.12+
  • Git
  • Postgres 16+ (all plugin state lives in Postgres)
  • A valid Douyin session cookie
  • Optional Cloudflare R2 credentials and bucket for archival uploads

Develop

git clone https://github.com/memenow/dyvine.git
cd dyvine
uv sync --all-extras
cp .env.example .env   # set DOUYIN_COOKIE, DATABASE_URL
docker run -d --name dyvine-pg \
  -e POSTGRES_USER=dyvine -e POSTGRES_PASSWORD=dyvine \
  -e POSTGRES_DB=dyvine -p 5432:5432 postgres:16
uv run alembic upgrade head

Validate

make test       # pytest
make coverage   # pytest with the 80% gate
make lint       # ruff + mypy
make format     # black + isort
make doctor     # hermes plugins doctor --ci (needs docker)

Optional R2 archival requires R2_ACCOUNT_ID, R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY, R2_BUCKET_NAME, and R2_ENDPOINT. The storage service auto-disables when any R2 field is empty.

Set DOUYIN_RETAIN_LOCAL_DOWNLOADS=true to run in local-retention mode: each task's files are kept under DOUYIN_DOWNLOAD_ROOT/tasks/<task_id> instead of being swept after upload, and the upload step is skipped while R2 is unconfigured. Retention also applies implicitly whenever R2 is unset, so a finished download is never discarded. Bound the retained workspace with DOUYIN_RETAIN_MAX_GB (GiB; 0 disables pruning).

Douyin's web APIs additionally require a per-request Argus webSign triple (uifid/timestamp/x-secsdk-web-signature) that only the SecureSDK inside a real browser session can compute. Dyvine keeps one headless-Chromium page purely as a signing session -- all traffic and downloads stay on plain HTTP -- starting it lazily on the first signed request (DOUYIN_WEBSIGN_ENABLED, default true; page DOUYIN_WEBSIGN_PAGE_URL; budgets DOUYIN_WEBSIGN_INIT_TIMEOUT_SECONDS and DOUYIN_WEBSIGN_SIGN_TIMEOUT_SECONDS), and re-signs once with a fresh session when it observes an Argus block (DOUYIN_WEBSIGN_RETRY_ONCE), and fails fast (backing off) after repeated signer failures. The host must provide a matching Chromium build (playwright install chromium); without it the builders return unsigned URLs exactly as before, so unaffected endpoints keep working while gated ones fail as HTTP 403. Set DOUYIN_WEBSIGN_ENABLED=false only as a kill-switch.

Persistence targets Postgres: set DATABASE_URL to a postgresql+asyncpg:// connection string and pick a pool strategy with DATABASE_POOL_CLASS: null (default) opens a fresh connection per use and holds none while idle, while queue keeps a capped pool tuned by DATABASE_POOL_SIZE, DATABASE_POOL_MAX_OVERFLOW, DATABASE_POOL_TIMEOUT, DATABASE_POOL_RECYCLE_SECONDS, and DATABASE_POOL_PRE_PING. DATABASE_OPERATION_RETENTION_DAYS bounds how long terminal operation rows are kept (0 disables purging), and DATABASE_JANITOR_INTERVAL_SECONDS (0 = disabled) controls the janitor heartbeat/sweep cadence. Apply schema changes with uv run alembic upgrade head.

Queue & Delivery SOP

The bundled dyvine:dyvine-ops skill carries the full batch-delivery SOP. The durable rules, condensed:

  • Never send a bare text probe: the first message in a delivery group is always the author's profile link + nickname.
  • Always deliver to a NEW group with the recipient as owner_id (an open_id starting with ou_ — never a plain user_id); never reuse an old group; dissolve superseded groups via DELETE /im/v1/chats/{chat_id}.
  • Paired batches: two accounts per batch; the previous batch must be fully delivered AND verified before local files are cleaned and the next batch starts.
  • Prefilters never retry: files over 30 MB are permanent failures (Feishu 234006); 0-byte files are deleted locally (Feishu 234010) and reported as incomplete posts.
  • Backfill dedupe: re-runs pass already_sent (exact paths from ALL history rounds) and known_permanent; a built group with zero delivered files (0/0) must be backfilled, never left.
  • Same-nickname accounts (distinct sec_user_ids) run strictly serially: download directories and progress keys are nickname-based.
  • Batch URL input: regex-extract v.douyin.com links from pasted share texts and resolve each with dyvine.users.resolve.
  • Leak scan orders each account's latest operation by created_at. Concentrated mass failures usually mean an expired DOUYIN_COOKIE; scattered interrupted after a refresh means Douyin-side volume throttling — converge over multiple rounds.

Periodic work is driven by hermes cron calling single-shot tools; the plugin runs no resident loops and holds no connections while idle.

Watch Mode

Watch Mode turns Dyvine from a request-driven downloader into a monitor. Each subscription targets one Douyin user and runs a long-lived asyncio loop with two independent polling cadences: a live-status check and a new-post check. When a live check finds the user streaming, it delegates to the livestream downloader (deduped by room_id). When a post check finds new content, it delegates to the incremental post downloader. Both paths create normal operation rows observable through the operation-polling tools.

Behavior and invariants

  • Each cadence uses monotonic due-times with +/−10% jitter so multiple subscriptions never hammer the upstream in lockstep.
  • With backfill_on_create=false (the default), the service snapshots the user's current first page of posts at creation time. The first post check then stops pagination at that boundary and downloads only posts published afterward.
  • New-post deduplication is membership-based using a bounded recent-aweme_id set (capped by DOUYIN_WATCH_RECENT_ID_CAP). The checkpoint is only advanced after a successful run so an interrupted cycle re-downloads at most the most-recent window, which the f2 downloader overwrites idempotently.
  • A live check delegates to the existing livestream downloader; a live-status miss or an already-in-progress recording is silently skipped.
  • Each triggered download creates a regular operation row (livestream_download or user_posts_incremental_download) pollable through the operation tools.
  • Subscriptions survive restarts: they are persisted in a dedicated watch_subscriptions Postgres table (same database as the operations table) and all enabled subscriptions are re-armed automatically on startup.
  • A crashed watcher loop restarts under exponential backoff and parks after 5 consecutive crashes; a parked subscription resumes only after delete-and-recreate.
  • Watch scheduling splits with WATCH_ENABLED: CRUD-only processes run with false (no loops run locally) while exactly one watcher process runs the loops and adopts new rows through a periodic reconcile pass.

Operations

Persistent State Store

src/dyvine/db/postgres.py persists operations, queue entries, seeds, send status, profiles, rounds, and watch subscriptions in Postgres (SQLAlchemy 2.0 async over asyncpg), connecting to DATABASE_URL. The schema is versioned by Alembic: run uv run alembic upgrade head before tools run against a new revision.

  • Every operation row carries an owner_id and a heartbeat timestamp.
  • With an explicit DATABASE_JANITOR_INTERVAL_SECONDS, the janitor heartbeats owned rows and fails rows whose owner went quiet; only genuinely orphaned rows are touched. Single processes run boot recovery plus a daily retention purge only, and never touch the database while idle.
  • Terminal rows older than DATABASE_OPERATION_RETENTION_DAYS are purged at boot and daily.
  • Read-only lookups never touch the stores; only real task execution opens database connections (pinned by tests/test_stateless_contract.py).
  • Unit tests inject in-memory fakes; the contract suite in tests/db/ runs identical assertions against both backends.

Background Task Lifecycle

Long-running downloads are scheduled through BackgroundTaskRegistry. During shutdown, tracked tasks drain before executor pools are reaped. State always lands in Postgres first, so a gateway restart loses at most in-flight progress, never records.

Idle Health

Repositories record each call's outcome in a DatabaseHealthTracker (unknown/available/unavailable plus a checked-at timestamp) observed from real calls, so idle health readers consult last-known state instead of probing. unknown counts as healthy.

Security Notes

  • Non-debug settings reject the placeholder database default.
  • Livestream URL validation only accepts douyin.com family hosts.
  • Output paths are checked before and after directory creation, including symlink segment detection.
  • Feishu credentials come from hermes defaults at runtime — never from the repo, Postgres, or logs. Never commit secrets, cookies, real user IDs, or local environment files.
  • Tool error messages stay human-readable and secret-free; the registry renders propagated errors.

Contributor workflow: create a feature branch from main, run make format && make lint && make test, and open a pull request.

Maintenance Notes

  • README.md is the concise maintainer entry point; keep it, .env.example, this page, and the contributor guide consistent when tools, configuration, or behavior changes. Automated contributors follow the contributor guide (AGENTS.md).
  • .env.example is the source of truth for supported environment variables and security defaults.
  • plugin.yaml provides_tools must mirror the tool table exactly; the bundled skill manual must name every tool. Both are test-pinned.
  • Runtime downloads, logs, and generated caches are local artifacts and should not be committed.
  • For Python behavior changes, run focused tests first, then make coverage before preparing a commit.
